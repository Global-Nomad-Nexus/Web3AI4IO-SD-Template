## 3. 先固定数据模型：防止采完再返工

### 3.1 身份和基本时间约定

1. 定义内部 `chain_key`：例如 `solana:mainnet`、`eip155:8453`、`eip155:56`。其中 Solana 写法是本项目内部约定；如要声明符合 CAIP 标准，另行核对标准格式并提供映射，不直接把内部别名称为标准 ID。
2. `token_id = chain_key + ':token:' + canonical_address`。EVM 比较键使用小写规范地址，并保留源地址；Solana base58 地址保留大小写。跨链同地址字节仍是两个 token_id。
3. 创建事件、代币、预测市场 outcome 使用不同命名空间；禁止用同一列 token_id 混装三者。
4. `event_time_utc` 表示链上事件时间，`retrieved_at_utc` 表示本次取得证据时间，`first_decoded_at_utc` 表示采集器首次解码时间。三者分别保存。
5. UTC 时间以带 Z 的 ISO 8601 或带时区时间类型保存；Unix 时间另注明单位为秒，避免毫秒混入。地址、签名、巨大 outcome ID、原始整数金额按字符串或精确整数保存，避免 Excel/浮点转换。
6. 人类可读名称、symbol、URL、token description 都不是可靠身份键。

### 4.3 P1 先探测能力，P3B 据此选完整枚举路径

每个候选公开 RPC 至少探测：窗口起点附近、中点、终点附近的历史 block/transaction；程序历史分页；版本化交易和内层指令返回；是否需要凭证；错误和限速。

输出 `source_capability.csv`：endpoint、method、目标日期、请求/响应状态、最早可得范围、分页是否可推进、耗时、实际记录数、是否满足公开条件。

能返回当前 slot 或一笔交易，不代表能返回整周历史；同一提供者的 HTTPS 和 HTTP/3 是传输备份，不能算独立来源。

### 4.4 P3B 第二步：独立枚举整个窗口

P3B 优先扩展 P2 已跑通的“必需 mint-authority PDA 完整交易索引 → 全部候选原生交易解码 → 区块哈希/时间补齐”路径，具体来源与验收见第 8.1 节。扩到其余日期前，逐日复核 create/create_v2 对该 PDA 的必需性和历史 IDL 适用性；P2 一日的适配证据不自动覆盖整周。下列程序历史分页与区块枚举保留为交叉核查或替代路径，不再把反复过载的 SQD 全 slot 扫描作为唯一完成方式。

**路径 A：程序历史分页。**

1. 对目标程序使用 `getSignaturesForAddress`，保存每页边界与 `before` 游标，逐页推进到创建窗口开始之前。
2. 对候选签名取交易，核对实际区块时间、执行成功、指令及 mint/creator。
3. 不按“取了若干页”停，也不把索引截断/空页自动视作已覆盖起点。
4. 程序调用范围、历史索引保留和分页可达性分别记账。

**路径 B：区块枚举。**

1. 找到覆盖 UTC 边界的 slot 区间，并读取两端邻近块验证时间边界；时间不可得的块单列，不能猜时间后直接纳入。
2. 用 `getBlocks` 分段取得实际返回的 block slots，再取块内交易。按实际 `blockTime` 最终过滤 `[start,end)`。
3. 区分链上跳过 slot、提供者缺历史和请求失败。缺块不是零创建；仅凭一个提供者的空返回不能断言是 skipped slot。
4. 解析外层、内层指令和版本化账户地址；同一创建的多种证据归一。最终性策略写入协议，保存区块/签名证据。
5. 正常不需要全链所有交易的全部经济分析；为了验证创建分母进行的区块扫描，和 Claire 的生态数据任务分开计算资源。

官方接口参考：[getSignaturesForAddress](https://solana.com/docs/rpc/http/getsignaturesforaddress)、[getBlocks](https://solana.com/docs/rpc/http/getblocks)。接口有单次范围和服务端限制，工程分块应小于实际可用上限；文档允许某个范围不等于任一公共提供者都会成功返回。

### 4.5 P3B 第三步：按集合对账，不只比总数

**P3B 已知起点：** 2026-10-08 UTC 的旧队列有 451 个 token_id，P2 重建有 55,508 个；交集 451 个，新增 55,057 个，旧集合未找到项为 0，交集中的签名、创建时间和 creator 一致。证据见 [P2 旧日逐条对账表](</Users/oushilin/Desktop/SRS/03 孜然/2026-10-27/registry_polymarket/p2/reports/legacy_day_identity_comparison.csv>)。这些是同日不同纳入流程的集合差异，不是已经裁定的 55,057 条采集故障，也不能据此外推其余六天。

设 A 为旧创建事件集合，B 为新重建集合，先统一事件键和 canonical creation 规则，再计算：

- `A ∩ B`：两次都识别；核对 token、creator、时间和版本是否一致。
- `B − A`：新增发现；标记 historical_backfill、取得时间和证据。
- `A − B`：旧记录本次未找到；先查历史源缺失、解码版本、边界差异或旧误收，不直接删币。
- 字段冲突：单独保存两个版本和裁定依据。

`creation_set_diff.parquet` 每行至少有事件键、token_id、差集类别、旧/新证据、原因、处理结果。两次数量相同但集合不同不算通过。

P3B 须独立枚举整个 `[2026-10-08, 2026-10-15)` UTC，按日及版本报告上述集合、字段冲突和覆盖。旧 event key 与 P2 原生调用树事件键的派生规则不同，先用稳定 token_id、签名和原生位置 crosswalk 对齐，再判断冲突。原因审计至少检查旧纳入规则（包括空 URI 条件）、发现/分页与预算、未取回交易、解码/执行状态、版本和边界差异。逐项保存旧代码/日志与新原生证据；证据不足标 `reason_unknown`，不得把全部差集归因于空 URI 或同一种漏采原因。

已知 4 笔交易是上述全窗口审计中的独立异常子集，不是全部差集的规模上限。取得准确签名后逐条归类：取回并成功解码、取回但非合格创建、仍取不回、版本未知。确认非合格也要保留排除证据；未找到原集群日志和签名前，保留这一组 4 笔及追查结果，不编造逐笔处置。

### 4.6 所有创建采集都要建立覆盖账本

`chain_query_ledger.parquet` 每行表示一段查询任务，不把“请求成功”直接等同于“范围完整”。至少记录：

`chain, platform_version, start/end_time, start/end_block_or_slot, source, method, cursor_or_chunk, attempted_at, response_status, expected_scope, returned_count, fetch_complete, decode_complete, unresolved_count, coverage_status, raw_ref`。

建议覆盖状态：

| 状态 | 条件 |
|---|---|
| complete_for_declared_scope | 声明范围的查询已闭合，版本适用已核对，无未解决获取/解码项，并有规定的覆盖核查证据 |
| partial | 已获得部分数据，但有明确缺块、分页中断、版本遗漏或未解码项 |
| unknown | 不能判断某区间是否已覆盖 |
| not_attempted | 尚未请求 |

“完整”只针对明确平台、版本、时间与查询设计，不等于整条 Solana 链所有平台。独立来源应说明提供者及底层来源；同源重复请求可以验证稳定性，不能宣称独立全覆盖证明。

正式版本目标仍是声明范围内全部合格创建。若历史公开源无法闭合，保留部分队列并明确限制，或在新协议中另设可验证窗口；不能不报告缺口却保留“全部创建”措辞。

### 4.7 P0 先转换旧队列，P3 补齐正式元数据视图

1. `event_key → token_id` 通过 crosswalk 连接；`request_id` 关联请求、快照与字段。
2. `metadata_observations` 保持字段长表，一条成功解析观察的 8 个登记字段不得误当 8 个代币。
3. `metadata_coverage` 包含所有 18,672 个旧计划检查点；失败观察即便无字段行也存在。
4. T0 按首次解码安排；T24/T48/T72 按创建区块时间加偏移安排。导出计划时间、真实请求起止、真实获取时间、相对创建延迟和旧时效标签。
5. 旧 `presence=present` 可包含 null；成功 JSON 中键缺失和请求失败分开。
6. 新补录币在历史 T0/T24/T48/T72 没有真实请求证据时，记录 `not_collected_historically`。现在重访可另留 `late_historical_followup`，不能补写成当年的 T0。
7. 最终追溯四个缺快照检查点；如正文/日志不可得，写成 evidence_missing，保留原终态与新的审计解释。

P3 导出时区分 `cohort_id` 与 `legacy_observed_cohort`：前者标识创建范围，后者标识是否属于旧 4,668 币观察队列；同一 token 可以属于正式创建队列并保留旧观察成员标记。旧六表及 18,672 个历史计划不扩写；新增补录币的历史检查点状态另存为 `not_collected_historically`（P2 原状态 `not_collected_historically_P2` 保留映射），不能记为请求失败、字段缺失或已完成观察。

覆盖报告必须分开给出分子、分母及实际时间规则：①旧队列内有合格历史 JSON 的币数/旧队列币数；②旧检查点的成功、失败、缺证据数/18,672；③正式创建集合中有对应历史观察的币数/正式创建币数；④新增补录集合中未历史采集的币数/新增补录币数。跨链/跨窗口分别统计，不把旧 4,668 或 18,672 当成三链共同分母；限定正式窗口内的旧队列子集时，另报该子集大小。新增币若现在重访，只生成带真实时间的独立观察。字段变化统计仅使用具有足够真实重复观察的币，并单列可比较分母。

### 4.8 P3B 输出与通过条件

输出：基线审计、legacy crosswalk、新创建事件/Registry、全窗口查询账本、逐日/版本事件差集及原因审计、异常队列、两个元数据视图、按队列区分分母的元数据覆盖报告、Solana 覆盖报告。

### 5.4 历史接口先探测，再选适配器

官方市场数据说明提供无需交易认证的公共读取路径；仍需按执行地点和时间实测可达性及历史范围，不把公开可读自动当成可再分发。参见 [Market Data Overview](https://docs.polymarket.com/market-data/overview)。

2026-10-27 查阅文档时可见两类价格历史端点：

| 接口 | 文档列出的参数与返回 | 实施要求 |
|---|---|---|
| `https://clob.polymarket.com/prices-history` | `market` 接 outcome asset ID，`startTs/endTs` 或 interval；`fidelity` 单位为分钟；返回 history 中的 t/p | 不把 market 参数误传为 Gamma market ID；实测所需日期及价格定义 |
| `https://data-api.polymarket.com/v2/prices-history` | `token_id`；显式 start/end、interval、as_of 选一种时间形式；返回 data、resolution_seconds 和分页 | 按返回 next_cursor 走完；保存分辨率、桶语义与结算点标记 |

来源：[CLOB 历史接口](https://docs.polymarket.com/api-reference/markets/get-prices-history)、[Data API 历史接口](https://docs.polymarket.com/api-reference/markets/get-a-tokens-price-history)。API 路径版本与市场协议版本是两个概念：不能看到 `/v2/` 就推断该 market 一定属于 Protocol V2。

建议探测顺序：

1. 选一个已核对规则、与目标日期有重叠的 market/outcome，先请求短范围。
2. 显式指定 UTC 起止；为了连接窗口第一天零点前的价格，额外请求至少覆盖最大允许陈旧度的前置时段，并留时间桶边界余量。
3. 优先让接口返回其实际可用分辨率，再按需要测试更细分辨率。不要默认“要日度”就能得到每个 UTC 日收盘值。
4. 若需细粒度，探测同一区间细/粗两档；空结果分别核查 ID、版本、日期、保留粒度、分页和服务错误，不自动解释为无交易。
5. 记录首末真实时间、记录数、实际间隔分布、重复/冲突、空缺日、有效变化和请求成本。
6. 检查历史序列末尾是否含结算支付点。结算结果留在结果表，不作为结算前交易者预期。`resolution_seconds=0` 可能表示真实 tick 或结算点，不能单凭 0 自动区分。
7. 当前订单簿、当前市场累计成交量和当前价格只作取得时点快照；不回填历史订单簿、历史日成交量或创建时价格。

Data API 文档还说明显式范围与历史粒度存在限制；本方案不把文档保留期限当作本项目已观测覆盖率。正式代码每次保存实际查询范围和响应粒度，长区间按当期接口限制分段。价格的定义若尚不能确认成交价/midpoint/抽样规则，保留为 `api_history_price_definition_unconfirmed`，可做接口示例，但不能悄悄改称日收盘或精确概率。

### 5.5 市场可用性分类

`polymarket_feasibility.csv` 每行一个候选 outcome × 目标窗口，至少有：

`market_key, outcome_key, topic, rules_checked, time_overlap, history_requested, history_obtained, actual_resolution_seconds, valid_points, covered_anchors, missing_anchors, price_definition_status, variation_summary, public_access_status, intended_use, decision_reason`。

分三级：

| 类别 | 判定 | 后续用途 |
|---|---|---|
| usable_for_alignment | 规则和对象清楚，有可解释的同窗历史，可以构造不含未来信息的价格 | 进入时间连接；即使价格不变，也可说明真实静态状态 |
| limited_for_demonstration | 同窗但稀疏、价格定义不清或长期不变，不能支撑变化分析 | 明确标记限制；不为“变化不足”删除不利市场 |
| catalogue_only | 无同窗历史、时期不适用或关联不成立 | 保留目录与原因，不硬接创建数据 |

“需要有足够变化”只针对拟做的变化分析，不作为事后挑选结果的标准。正式候选集合按主题、期限、覆盖等先验规则确定，未选中的候选仍报告。

### 5.6 可选历史档案

老师提到的 [TimeSeventeen/Polymarket-v1](https://huggingface.co/datasets/TimeSeventeen/Polymarket-v1) 数据卡列出 CC BY 4.0，论文说明 v1 档案覆盖 2022-11-21 至 2026-04-28。它可以调查老师所列早期市场，但**不能补出 2026 年 10 月窗口的预期**。

先读 schema、市场元数据、日期分区和授权说明，按相关 market/condition/outcome 筛选，再决定是否下载对应分区。不要先下载整库。若从成交日志重建日价格，另写成交方向、金额精度、去重和聚合方法，不与 API 历史价格无标记拼接。保存数据集 revision、分区路径和来源。

### 5.7 P1 交付证据与扩展条件

P1 输出少量候选的搜索日志、真实规则/outcome/历史价格、单币时间连接和三链来源能力报告；完整候选目录和批量数据层在 P2/P3 继续建立。字段有则采、无则标明，不因尚无历史成交活动全表阻塞一条真实价格连接。

最小通过条件：至少一个市场具备已核对身份/规则、真实历史点、明确时间语义和可复现取得记录，并能在目标窗口构造有效锚点。若这一条件不满足，先修正来源/窗口策略，不启动全量 Polymarket 下载，也不以当前价格替代。

每次真实探测后立即更新个人 Methods 中的市场筛选、API 和价格时间段落，Technical Validation 中的实际覆盖，Usage Notes 中的一条有效连接示例。空结果和限制同样入稿，不等 P4 才回忆方法。

若没有一个市场能与旧七日窗口有效重叠，旧七日成果继续保存；三链整合另选预先声明、数据可得的共同窗口，或建立新的前瞻采集。不能为兼容一条 2025 年市场记录而把它当作 2026 年实时预期。

## 6. 预期映射和时间连接：本项目最容易出错的部分

### 6.1 四类关系和证据

| link_type | target | 证据门槛 | 解释边界 |
|---|---|---|---|
| verified_token_identity | 特定 token_id | 规则/官方来源能唯一核实链与地址；必要时附经核验的地址链接 | 同名、symbol 相同、搜索命中都不够 |
| platform | 平台及版本/时期 | 题目规则明确指向平台和事件范围 | “任一 Pump.fun 币上市”不是每币上市概率 |
| chain | chain_key | 规则明确指向 SOL、BNB 或 Base 生态 | 原生币预期是链背景，不是每个新币价格预测 |
| shared_economic_event | economic_event_id | 同一次可识别的决议/发布及时间 | 同一背景可以连接三链，但不是三份独立预期 |

每条映射至少保存：`mapping_id, link_type, target_type, target_id, pm_market_key, pm_outcome_key, rule_snapshot_ref, evidence_ref, semantic_valid_from/to, rule_known_from_utc, mapping_created_at_utc, reviewed_by, review_status, uncertainty`。

`semantic_valid_*` 描述这条关系适用的时期，`mapping_created_at` 描述研究者何时建立映射，二者不同。回溯建立链背景关系可以用于历史整理；若要声称当时可用的预测特征，还需核验规则与合格对象的当时可知性。无法证明时标记 retrospective_mapping，不能用事后名单构建事前特征。

### 6.2 逐币创建时连接规则

对创建时刻 `t_i` 与某条已通过审核的映射 m，选择在该时刻以前已经形成的最后有效价格：

```text
eligible_price =
    同一固定 market + outcome
    AND mapping 在该锚点适用
    AND 价格信息有效结束时间 < t_i
    AND 不是结算支付点
    AND 尚未越过该市场的有效预期结束边界
    AND t_i - 价格信息有效结束时间 <= 预设最大陈旧度

selected = eligible_price 中有效结束时间最近的一条
```

默认采用严格早于锚点，避免只有秒级时间、无法确定同秒先后时误引未来信息。同秒排序若有可信细粒度证据，可另设规则并记录。

关键是“价格信息有效结束时间”，不能只看 API 返回的 timestamp：

- 精确 tick：按源时间及其时间精度处理。
- 时间桶：先验证 timestamp 标的是桶起点、桶终点还是其他采样时刻；若聚合使用整个桶，只有桶结束后才可用于后续创建。
- 不知道桶语义：不能直接把标记为 09:00 的点用于 09:05 的创建；先排除事前用途或采用经文档/实测支持的保守延迟规则。
- 当前请求时间晚于创建时间不使历史记录自动失效；但必须有历史源时刻和形成规则。反过来，当前 metadata/规则不能无证据回填为当时状态。

保存 `anchor_time, source_timestamp, bucket_start/end, effective_information_time, price_age_hours, is_stale, source_retrieved_at, time_semantics_status`，使任何连接都能审计。

### 6.3 日度连接规则

定义 UTC 日 d 的起点为 `d 00:00:00Z`：

- `launch_count_d`：该 UTC 日 `[d,d+1day)` 内不同 canonical token_id 的创建数，同时附创建覆盖状态。
- `expectation_at_day_start_d`：严格早于日初、仍有效且不过期的最后价格。
- 不使用当日均价、当天收盘或事后结算值去解释同一天全部创建。
- 24 小时最大陈旧度是建议主参数，12/48 小时作敏感性检查；阈值在正式生成前固定，并报告覆盖变化，不择优选择更好看的结果。
- 过期、结算、关闭后的值不自动延续。不同期限或阈值的市场不拼成一条线，除非另有明确滚动合约定义与切换规则。

**说明用假想例子，以下不是实采结果：** token 于 10:15 创建；若历史点 10:00 是 10:00–11:00 的整桶统计，该点不能用于 10:15；若 09:00–10:00 桶在 10:00 已形成且规则已确认，则可作为候选。日度 00:00 锚点也不得使用当日 00:00–24:00 的汇总。

### 6.4 未匹配、背景匹配和连接行数

建议 `pm_match_status` 采用：`matched_valid, no_candidate, no_verified_identity, no_temporal_overlap, history_unavailable, request_failed, stale_price, market_not_open, market_closed_or_resolved, unverified_time_semantics, mapping_unverified`。

这些原因可以同时存在；允许保存多个 reason_code，另指定 primary_reason 的优先顺序，避免统计时重复加总。不能把未匹配填为 0、0.5 或“预测失败”。

Registry 左连接长表后，一币可能匹配多个市场，行数增加是正常的。统计母体用不同 token_id；日背景直接在链—平台—日粒度生成，避免把同一条宏观预期复制成几千个独立样本。未匹配币用明确空引用行或独立覆盖表保留，不对不存在的 mapping 编造 ID。

### 6.5 必须分别报告的覆盖指标

1. **直接身份匹配率**：有 verified_token_identity 的不同币数 / Registry 不同币数；另报其中创建锚点具备有效历史价格的币数。没有直接匹配是允许且可能常见的结果。
2. **背景日覆盖率**：在声明的链—平台—UTC 日网格中，至少有一个合格背景预期的格数 / 全部声明格数；另按创建覆盖完整的格子报告可共同分析比例。
3. **创建锚点预期覆盖率**：创建时有至少一条有效背景/身份预期的不同币数 / Registry 不同币数，按关系类型拆开。
4. **市场历史锚点覆盖率**：各 market/outcome 在有效研究区间内可构造的日初锚点数 / 预期应评估锚点数；开市前、有效期外与请求缺失分别报告。

保留分子和分母；分母为 0 时写不适用，不写 0%。直接身份匹配和背景可用性不能合称一个“匹配率”。

## 7. P2：三链共同短窗口整合试点

目标：为 Solana、Base、BSC 各产出一个基于全窗口合格创建的真实整合样例。

### 7.1 选择窗口的固定程序

1. 优先探测旧七日区间内三链与 Polymarket 是否均有历史能力。
2. 若可行，在事先列出的候选日期中按固定顺序选第一个满足技术条件的完整 UTC 日；保存全部候选和不满足原因。
3. 若旧窗口不可行，选择最近可完整核验的共同历史日，或事先固定未来窗口并前瞻采集；写明这是独立试点 cohort。
4. 完整 UTC 日没有合格创建时，保留该零结果；可以按预先规定扩大时长，另建协议版本，但不替换为热门币列表。
5. 窗口选择依据是可观测性与资源，不是价格变化方向、毕业数量、显著性或“故事性”。

### 7.2 Base/Clanker 与 BSC/Four.meme 的具体步骤

1. 从已有平台登记和官方仓库查工厂/管理器地址、ABI、创建事件定义及生效范围。分别固定历史版本；不能只取当前最新工厂。
2. 在 EVM 链上按块时间定位 `[start,end)` 的边界块，再按每个有效工厂、事件 topic 和 block 区间查询 `eth_getLogs`。
3. 若返回超限/截断，缩小区间直到请求能够闭合，保存所有子区间；分块边界防重，不能静默跳过超大响应。
4. 核对日志发出合约、topic、transaction receipt、执行状态和 block timestamp；取回必要交易输入，明确 creator 的字段角色。
5. 对可疑空区间用更小块请求、receipt/区块级核查或独立来源检查，防止把接口缺失当零创建。
6. 对临近链头数据遵循最终性策略；历史和实时均保存 block hash，遇重组重新核对并标记替换记录。
7. 创建必须有明确创建证据；ERC-20 Transfer、首次观察到地址、建池、交易和迁移不自动算创建。

技术入口：[Ethereum JSON-RPC](https://ethereum.org/en/developers/docs/apis/json-rpc/)、[Clanker 官方 SDK](https://github.com/clanker-devco/clanker-sdk)、[Four.meme 官方集成仓库](https://github.com/four-meme-community/four-meme-ai)。只参考其地址、布局与机制资料；本研究采集不需要部署代币或提交交易。

### 7.3 三链共同输出

按第 3 节 schema 输出 creation_events 和 Registry；保留各链原生字段。对每币应用第 6 节的映射与时间规则，可以共享同一经济事件，不要求每个普通新币都有直接预测市场。

每链至少提供：

- 窗口与版本说明、全窗口合格创建表、可回溯链上证据。
- 同窗真实 market/outcome、规则、价格记录、映射和连接输出。
- 未匹配/无历史/时间不适用记录与具体原因。
- 整合前后不同 token_id 数量、关系类型计数、创建和预期覆盖。
- 一段从固定输入生成样例输出的可复现代码。

展示时可以抽出每链前 5–10 条（按创建时间和 ID 固定排序）放进 README，但底层必须保留整个窗口；不能把几行展示表误称为完整样本。

### 7.4 P2 通过条件

| 检查 | 通过标准 |
|---|---|
| 创建身份 | 三链各有明确的纳入规则、原生证据和链限定 ID |
| 查询范围 | 全部查询分块有终态，未解决覆盖缺口单列 |

| 未匹配 | 未匹配代币被保留且有状态说明 |

若某链窗口内确为零合格创建或无有效预期，报告事实与限制；该结果可以完成能力试验，但尚不能声称已交出该链非空的创建—预期整合样例。随后按预先记录的规则另选/扩大演示范围，保留原试验结果。

### 8.4 P5 使用的生命周期事件定义；P4 先保留为草案

建议受控事件：`created, first_observed_trade, graduated, migrated, venue_added, liquidity_changed, inactivity_started, reactivated, last_observed_activity, terminal_outcome`。

- **首次交易**：只有从创建以来目标场所历史足够完整时，才称 lifetime first_trade；否则保留 first_observed_trade，并注明观察起点。
- **毕业/迁移**：需要平台具体事件或可核实机制证据；不是自动的经济成功或死亡。
- **后续场所**：迁移后继续跟踪已核实目的池与后续场所；未覆盖的场所写缺口，不能自动视作没有活动。
- **不活跃**：某个预先定义的活动范围内连续无合格交易，并且对应区间有足够覆盖；7/14 日是候选阈值，不是普适死亡标准。
- **重新活跃**：被判不活跃后再次出现合格活动，保留两次状态转换。
- **终止结局**：仅在预设、证据支持的不可逆或明确终止定义下标记，并保留证据；无法证明时继续随访到 cutoff。

生命周期可能往返，不应强行压成只向前的单条“创建→交易→毕业→死亡”路径。暂时不活跃不会自动触发永久停止随访。

### 8.5 P5 真实随访与删失；P4 只测试这些逻辑

1. 每币从实际创建时刻开始，按各层实际可观测范围跟踪到共同 cutoff，或证据支持的目标终止事件。
2. `last_activity_at` 是最后活动时间；`last_observable_at` 是最后有覆盖证据的观察时间。不能把最后活动时间直接作为事件“死亡”时间。
3. 对每个目标结局分别保存 event_observed、event_time、followup_end、censoring_type、coverage_grade。首次交易、毕业和某个终止结局有不同风险集和删失状态。
4. 若完整观察到 cutoff、仍未出现该目标结局，记 administrative_right_censored，删失时间为 cutoff。
5. 若提前失去覆盖，保留 loss_to_followup/unknown；仅在预先规定的分析中按最后可信可观测时间删失，并报告其可能并非独立删失，不能标成完整追踪到 cutoff。
6. 事件只知道发生在两次观察之间时，保存区间界限，不能伪造精确时间；需要精确时间的分析应另处理。
7. 从出生开始历史缺失的币，不能把它伪装为完整出生队列；延迟进入、左侧历史缺失和普通右删失应分开。
8. never-traded 只能在声明交易场所与覆盖范围内成立；从创建到 cutoff 数据不足时标 unknown。never-migrated 同理。

元数据访问失败、没有社交账号、未毕业都不作为死亡证据。主包不必为了完成任务强造“死亡”标签；可以发布明确的活动状态、覆盖和逐目标删失结果。

### 9.5 资源与运行监控

```text
预计时间 ≈ 任务请求量 / 实测有效吞吐 + 重试与解析开销
预计存储 ≈ 同类短窗口实测字节 × 时间/事件扩展系数
```

## 14. 失败时如何调整路径

| 情况 | 立即动作 | 不应采用的处理 |
|---|---|---|
| 旧周 Solana 历史无法完整取回 | 保存 partial/unknown 区间；核查其他合格公开源；必要时新建前瞻队列 | 将请求失败记零、只补长空档后宣称全量 |
| 某历史平台版本 ABI/IDL 缺失 | 保存原始证据和 undecoded；核对历史官方版本，缩小已证实范围另发协议 | 用最新 ABI 强行解码旧事件 |
| Polymarket 空历史 | 查 ID 类型、版本、时间范围、分辨率、分页和保留；保留失败证据 | 用当前价格、结算值或 0.5 回填 |
| 老师例举市场不在正式窗口 | 进背景目录；找有同窗历史且语义成立的其他题目 | 跨年份平移价格 |
| 没有普通新币直接市场 | 用 chain/platform/shared economic event，单独报告零直接匹配 | 按名称模糊匹配并称身份核验 |
| 公开源要求申请、付费或私钥 | 寻找满足要求的公开来源；未找到则列未达标依赖 | 使用个人权限完成后声称公众可复现 |
| 重跑历史 metadata 内容变了 | 记录新的 observation，保留旧摘要与复现限制 | 修改旧值和旧获取时间 |
| P0–P4 没有 Claire 真实数据 | 按既定顺序完成全部个人数据、图集、初稿和接口测试，状态 awaiting_integration | 把这件事当个人阻塞，或把空列/fixture 当真实整合 |
| P5 发现接口或范围不一致 | 版本化字段适配、列出差异和受影响表图，保留个人原始证据 | 静默覆盖真实创建、丢弃未匹配币、回写采集时钟 |
| 迁移后交易找不到 | 追目的池/场所与覆盖；无法覆盖标 unknown | 将迁移视作死亡或观察终点 |
| 价格不变/小样本 | 如实画与报覆盖，不做显著性结论 | 为得到相关性换市场、挑日期、复制宏观样本 |
| 图表与文中数不同 | 回到同一冻结表重新生成 | 直接手改图中文字凑一致 |
