## 摘要

P3 将 P2 的三链整日试点扩展至同一完整 UTC 周，在声明的 Pump.fun 创建指令、六个 Clanker 工厂及 Four.meme V2 创建事件范围内，建立了 **367,373 个不同代币**的创建 Registry。共同窗口为 **[2026-10-08 00:00:00, 2026-10-15 00:00:00) UTC**，对应北京时间 10 月 8 日 08:00 至 10 月 15 日 08:00。三链七日共 **21 个链／日范围全部闭合**。

最终数据包含 Solana 330,061 个币、Base 1,535 个币和 BSC 35,777 个币。Polymarket 部分保存 445 条“类别—候选市场”记录，去重后为 405 个候选市场；其中详细保存 60 个市场、120 个原生 outcome，以及 175,054 个历史价格点。对 60 个市场的 16 种不同规则全文完成核对，形成 28 条 Yes outcome 映射：22 条链背景、5 条共享经济事件背景和 1 条平台背景，**直接币身份映射为 0**。

逐币预期长表共有 **6,156,902 行连接评估记录**。其中 **5,856,212 行为有效连接**，另有 **300,690 行因映射超出有效期而保留状态与空价格**。这些行是代币与市场映射的组合，不是同等数量的独立代币或独立经济样本。

旧七日队列的 4,668 个 Solana 代币全部在本次重建中找到，旧币未找到数和关键字段冲突数均为 0；另新增重建 325,393 个 Solana 创建身份。旧 18,672 个元数据计划和 133,888 条字段观察保持原样，没有为历史补录币伪造 T0/T24/T48/T72 观察。

最终 **35 项数据验收全部通过、失败为 0、待完成覆盖为 0**。固定种子原生 QA 覆盖 191 个样本、14 个分组；在禁止网络的条件下连续重建两次，15 张 processed CSV 的哈希逐一一致。P3 因此完成其声明范围内的数据构建；历史规则版本、API 价格标量定义、原始旧元数据正文及真实生命周期的限制继续保留。[E01] [E02] [E03] [E04]

## 1. 实验目的与阶段位置

### 1.1 P3 要解决的问题

P3 的工作分为两部分。

| 部分 | 研究与工程问题 | 实际交付 |
|---|---|---|
| P3A：正式三链创建与预期层 | 能否在同一时间窗内枚举声明平台范围的合格创建，并连接创建前已经形成的市场价格背景 | 三链 Registry、创建事件表、原生证据、市场与 outcome、规则快照、历史价格、映射、逐币预期及日背景 |
| P3B：旧七日审计与元数据保留 | 旧队列与重新枚举的创建集合有什么差异；哪些元数据是真正历史观察，哪些币当时没有采集 | 整周集合差集、旧事件键 crosswalk、元数据观察与覆盖表、异常与未知原因记录 |

P0 建立了旧六表、身份、异常与输入锁；P1 验证了公开来源和历史价格时间连接的有限可行性；P2 跑通 2026-10-08 一个完整 UTC 日的三链链路，得到 61,916 个币。P3 在这些证据和代码基础上，完成七日共同窗口，而不是把 P2 单日结果直接复制成七日结论。[E05]

### 1.2 完成标准

P3 的通过条件包括：声明范围闭合、候选交易全部解决、创建身份与外键成立、原生执行和区块证据一致、价格满足严格的时间连接规则、创建母表不因匹配失败而丢币、旧周审计与元数据保留成立、规则审核完成、固定输入可复现。

这里的“完成”限于 P3。完整出版图集、个人交付候选与生命周期接口属于 P4；真实生态与生命周期接入、共同 cutoff、联合验证及发布属于 P5。最终配置仍为 `lifecycle_enabled = false`、`common_cutoff_utc = null`，联合状态为 `awaiting_integration`。[E01] [E05]

## 4. 实验过程与版本修复

### 4.1 准备与试运行

正式采集前，P3 先建立独立目录、输入锁、单写入锁、显式正式启动参数、请求／字节／时间预算和缓存校验。准备阶段通过 49 项隔离测试；从 P2 原生证据重新解码 61,916 个创建，身份和关键字段差异为 0，并完成两次离线重建。

准备阶段的全链路回放不替代正式七日验收。此时其余六日和正式市场调查仍显式 pending，直到用户授权正式运行后才扩大到共同周窗口。[E10]

### 4.2 正式采集和持续保存

正式运行按日、链和分页／区间写入进度。成功请求按固定键缓存并校验哈希；候选索引、完整交易页、区块段、已完成回执、失败原因持续落盘。同一输出目录由单写入锁保护，续跑前先确认上一轮退出。

完整继承运行历史保存 **30 条调用回执**：2 条带保存检查点的停止、11 条“完整性通过但 P3 覆盖待完成”、16 条“采集覆盖待完成”、1 条最终通过。它们是同一个冻结实验的连续调用记录，不是 30 组独立抽样实验。[E06]

### 4.4 接口失败与资源使用

最终继承的请求账本有 **10,710 条请求记录**，其中 9,877 条 `ok=true`，826 条为 HTTP 529，另有 2 条 HTTP 200 但应用／读取层失败，以及 5 条无 HTTP 状态的传输或解析连接失败。HTTP 200 本身没有被直接当作成功。历史失败包含 Method not found、连接重置、超时和 DNS 失败，均留在原始账本中。[E09] [E12]

## 5. 实验方法

### 5.1 原生时间边界与历史布局验证

每个 UTC 日先定位“第一个不早于边界时刻的实际区块／已产生 slot”，再取得前一个实际区块，要求：

`previous_time < target_time <= first_time`。

开始与结束边界分别留存原始证据。Solana 跳过的 slot 不直接当作缺失创建或零创建；程序先验证实际产生的位置。

Pump.fun 每日读取 IDL 的历史前驱提交及当日变更，核对 create/create_v2 discriminator、mint 与 mint_authority 的账户位置、必需 PDA 派生和 name/symbol/uri/creator 参数前缀。EVM 每个地址／事件使用固定 ABI 和哈希；这证明此次声明布局下的解码适用性，不额外宣称完整代理升级史。

### 5.2 Solana：完整候选索引与执行判定

采集从创建指令要求使用的必需 mint-authority PDA 建立候选交易索引。先证明窗口后的实际账户交易锚点，再使用官方 getSignaturesForAddress 逆向分页，直到越过窗口开始。候选要求 finalized、有时间、页内外无重复且顺序可核对。

Vibe 负责获取同一账户、slot 与时间范围的完整历史交易。两种来源按签名逐一核对 slot、blockTime 和交易错误状态；多出签名或已见字段冲突均停止。七日官方候选共 **359,657 笔交易**，全部解决。候选交易数与最终创建事件数不同：一笔候选交易可能没有合格创建，或包含被识别但失败／回滚的指令，不能将二者直接相减解释为遗漏数。

10 月 14 日的完整 Vibe 分页比官方索引少 24 笔。程序保留原分页，对这 24 笔分别使用官方 getTransaction 取得完整内容，并使用 getBlock 的签名列表证明交易顺序，再核对必需 PDA、slot、时间、状态与区块哈希。24 笔不是被静默删除的候选，也不等于新增 24 个币。[E11] [E13]

创建资格由调用树、交易日志、交易错误与指令提交状态共同决定。明确失败或回滚的指令排除；未知内层提交状态只允许以指定单 slot 的归档原生证据补核，未解决时不能标完成。候选 slot 的头证据另外通过 CryptoHouse 保存，并与完整交易时间核对。最终新采集日的回执均为 `unknown_commitments = 0`。

### 5.3 Base 与 BSC：位置覆盖、日志和 receipt 核对

Base 在六个固定地址、固定 topic 中按明确区块区间调用 eth_getLogs。BSC 在固定 Four.meme V2 地址／topic 中使用 SQD，单次不超过 1,000 块，设置 includeAllBlocks，并要求返回头从区间起点连续到下一检查点。

取得候选日志后，两链都获取全部相应交易 receipt 和有事件区块的原生头，核对：

1. 交易成功状态、交易哈希及所属区块号；
2. receipt、归档日志与区块头的哈希一致；
3. 交易顺序 transactionIndex 和事件顺序 logIndex；
4. 原生 receipt 中恰好存在相应日志，地址、topic、data 相同；
5. 日志未被 removed，且固定 ABI 可以准确解码；
6. 原生区块时间位于声明 UTC 日内。

v5 对 SQD 父 header 字段的修复仅补回同一原始响应内已存在的区块身份，不代替独立 RPC 核验。

### 5.4 稳定身份、创建字段与入组规则

代币身份由“链标识＋规范化地址”构造。EVM 地址规范化为小写；Solana 地址保留原始大小写。相同地址字符串在不同链上仍为不同 token_id。

创建事件身份由“链＋交易签名／哈希＋原生指令路径或日志位置”确定。一个代币出现多个冲突创建身份时立即进入冲突处理，而不是任意选择。最终 `creation_events` 与 `registry` 均为 367,373 行，满足当前一币一创建约束。

创建资格不要求 URI 非空、URI 可访问、后续发生交易、毕业、迁移或匹配到 Polymarket。creator 的角色按原生定义保存：

| 平台／版本 | creator 的定义 |
|---|---|
| Pump.fun | 指令 creator 参数；与 user signer、fee payer 分列 |
| Four.meme V2 | TokenCreate.creator |
| Clanker v4 | TokenCreated.tokenAdmin |

这些地址不是经过识别的自然人。不同平台的角色也不应未经转换就视为同一种经济主体。

### 5.5 Polymarket 有界搜索和候选选择

搜索覆盖七类主题：Base token、BNB、宏观利率／通胀、Pump.fun 上币、收入、发售及 Solana。每个关键词均请求 active 与 closed 状态，展开 event 的子 market，保存候选和具体停止原因。

配置上限包括：每个关键词／状态最多 3 页、每类别按稳定 market ID 选择最多 12 个时间重叠候选、历史获取最多 120 个 outcome，历史按 3 日区间分页、每 outcome／区间最多 16 页。候选选择在读取价格结果之前确定，避免依据价格高低挑选。

类别之间存在重叠，同一市场可能出现在多个类别中；旧 P1 种子市场也继续保留。因此类别统计可以出现 13 个详细市场，不能据此将类别分母简单相加成独立市场数。BNB 与 Solana 类别达到有界搜索上限，保留 `bounded_not_exhaustive`，不声称已经穷尽全部 Polymarket 市场。

### 5.6 完整规则审核与四类映射

审核读取问题、全部规则正文、Yes/No、开启时间、计划结束时间、实际关闭时间与对象范围，并绑定准确 rules_sha256。规则变化后，旧结论不能自动迁移。

| 映射类型 | 成立要求 | 本次条数 | 解释 |
|---|---|---:|---|
| verified_token_identity | 有独立地址证据，能够指向具体 token_id | 0 | 没有已核实的单币身份连接 |
| platform | 规则针对平台层面事件 | 1 | Pump.fun 上币背景 |
| chain | 规则针对链或该链资产／发币主题 | 22 | Solana 11、BNB 10、Base 1 |
| shared_economic_event | 明确的宏观经济事件定义 | 5 | 可作为三链共享背景 |

审核最终形成 120 行 outcome 审核表、60 行逐市场审核证据，涉及 16 种不同规则全文。28 条映射均选择 Yes；No outcome 的真实历史仍保留在数据中，但没有重复作为互补特征加入。

搜索命中并不自动成立语义连接。PUMP/USDT 阈值市场属于平台币价格，不被解释为 Pump.fun 收入、募资或任意新币上市；NYSE 选择结算链不被解释为 Base 发币；市场 2007290 的规则针对符合特定毕业与上市条件的任意 token，它只作为 pump_listing 的平台背景，不能解释为当前每个 mint 的上市概率。收入与发售类别的最终可连接 outcome 均为 0。[E14]

所有映射标为 `retrospective_mapping`。规则快照在本次取证时取得，完整历史修订档案未取得，`rule_known_from_utc` 留空。价格时钟约束通过，仍不能据此认证研究者在创建当时已经知道完全相同的规则与映射。

### 5.7 严格 as-of 价格连接

对一个起点为 s、宽度为 Δ 秒的价格桶，将有效信息时间设为：

`effective_information_time = s + Δ`。

对创建时刻或日初锚点 T，在指定 outcome 和经过审核的分辨率系列内，选取有效信息时间最大的价格点，并要求：

- Δ > 0，价格有限且处于 [0, 1]；
- `effective_information_time < T`，等于锚点的价格也不使用；
- 锚点与价格信息时间之差不超过主阈值 24 小时；
- 锚点位于市场开放及审核语义有效期内；
- 已达到计划关闭、实际关闭或 resolved 时间中的最早时刻后，不再连接。

零分辨率点只留证，全部排除。混合分辨率不静默拼接：4 条 P1 映射明确使用 1,800 秒系列，24 条新增映射使用 300 秒系列。对同一 outcome／时间／分辨率出现不同价格的情况停止处理。

同样的方法用于日初背景，并执行 12 小时与 48 小时陈旧度敏感性。连接失败保留具体状态与空值，不使用 0 替代未知价格。

### 5.8 旧七日集合对账与元数据转换

旧队列与新 Registry 先按 token_id 连接，再逐日核对交集、新增、旧币未找到和关键字段冲突。不同事件键通过 crosswalk 保留，不覆盖旧键。

旧 4,668 个币的四个计划检查点 T0/T24/T48/T72 共 18,672 行保持不变。T0 按原首次解码时钟理解，T24/T48/T72 保留原计划依据；实际完成时间、晚到状态、请求失败及解析失败分别记录。没有用本次历史补录时间回填旧首次观察时间。

补录币统一标识 `not_collected_historically`，不新增其历史计划。旧表缺少原始 HTTP 正文时，字段记录作为旧存档观察保留，不将本次表间复核称为重新执行原始 JSON 解析。

## 11. 结果的解释边界

### 11.1 本次结果能够支持的使用

当前数据可以用于核实声明范围内的创建身份、比较平台和日期的描述性创建数量、复现创建时点与市场背景的时间连接、研究元数据可观测性，以及为后续生态／生命周期数据提供稳定的 token_id 母表。

对创建表的完整性、历史观察的覆盖、市场连接的可用性分别提供了分母。研究者可以只选取 matched_valid 的价格记录，也可以使用完整评估表研究为什么某些映射在某个时点不适用。

### 11.2 仍不能由 P3 单独得出的结论

| 限制 | 对解释的影响 |
|---|---|
| 创建覆盖限于固定地址、topic/discriminator 和布局 | 不能称为三链全部 Token 或所有平台发行普查 |
| 市场调查有预算且两类未穷尽 | 不能将未匹配解释为 Polymarket 一定不存在相关市场 |
| 直接币身份映射为 0 | 背景价格不能解释为单币成功、上市或存活概率 |
| API scalar 构造未确认 | 不能默认其等于成交量加权价、midpoint、可执行价或经过校准的概率 |
| 历史规则修订档案未取得 | 严格先于锚点的价格，不自动成为已认证的事前可知特征 |
| 历史活动量未取得 | 当前 active/closed 快照不等于历史流动性、成交量或参与度 |
| 元数据历史覆盖仅限旧观察队列 | 新补录币的缺失不能当作当时没有元数据，也不能用当前抓取伪装历史观察 |
| 旧正文和精确签名仍有缺口 | 旧异常不能被宣称全部恢复或逐条解释 |
| 生命周期与共同 cutoff 未接入 | 无法由 P3 得出后续交易、毕业、迁移、存活或终局结论 |
| 一周观察与共享背景重复 | 无法仅据跨链差异或长表行数建立因果结论 |

最终价格特征状态仍为 **retrospective_demonstration_only**。报告中的“时间约束通过”指已编码、已核对的历史价格时钟与有效期规则；它不是对完整信息可得性、市场效率或因果识别的认证。

### 11.3 正确读取与连接建议

使用 token_id 将其他表左连接到 Registry，保留没有价格、没有历史元数据或尚无生命周期信息的币。价格分析先检查 match_status、link_type、feature_readiness 和 effective_information_time_utc；不要只读取 price 一列。

metadata_observations 与 metadata_coverage 应一起使用：字段值、请求终态、时间状态和原始证据是否存在是不同维度。后续接入生命周期时，需要单独冻结共同 cutoff、观察终点及缺失／删失定义，然后运行新的联合验收。
