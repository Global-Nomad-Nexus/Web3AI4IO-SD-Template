## 3. 数据从哪里来

### 3.1 链上事件

采集器通过 Solana JSON-RPC 查询 Pump.fun 程序，按 `create` 与 `create_v2` 的八字节 discriminator 识别创建指令。`mint` 取账户 index 0，`creator` 从指令参数中 `name`、`symbol`、`uri` 后面的公钥解码，`metadata_uri` 来自该指令的声明。

每个事件用网络、交易签名及指令位置生成稳定的 `event_key`。元数据请求失败不删除事件，后续统计继续保留该分母。

RPC 配置顺序为 PublicNode HTTPS、同一 PublicNode 地址的 HTTP/3，最后是官方 Solana RPC。连接记录显示 PublicNode 两种传输方式均曾被选中；官方 RPC 的尝试记录为失败。两种 PublicNode 传输方式共用提供者，不能作为两条独立来源的覆盖验证。

### 3.2 元数据请求与网关

采集器先检查链上声明 URI 的路线是否允许访问。允许时先请求声明路线；能识别 IPFS CID 的声明，在路线被拒绝或发生可重试失败后，可以通过登记网关请求同一 CID。`uri` 保留原声明，`request_url` 和 `route_id` 记录实际路线。

请求使用 HTTP GET，不跟随重定向、不保存 cookie、不执行 JavaScript。响应上限为 1,000,000 字节。本地地址、私有地址及来源登记明确拒绝的路线在连接前留下记录。

| 请求表状态 | 行数 | 含义 |
|---|---:|---|
| `success` | 16,748 | 传输层记为成功，不保证已形成可解析快照 |
| `http_error` | 19,676 | HTTP 错误 |
| `timeout` | 7,534 | 请求超时 |
| `transport_error` | 3,957 | 连接或传输错误 |
| `route_refused_policy` | 12,864 | 路线被拒绝，未发出该次网络请求 |
| 合计 | 60,779 | 请求尝试及拒绝记录 |

12,864 条路线拒绝均对应 `ipfs.io`。拒绝后仍可尝试同 CID 的允许网关，因此路线拒绝次数不等于最终失败的观察数。

响应快照中最多的实际主机是 `pump.mypinata.cloud`，有 11,540 条，其次是 `metadata.j7tracker.io` 的 2,912 条。这里按响应快照计数，不是按代币数计数。

### 3.3 字段与六张表

解析器只读取八个顶层键：`name`、`symbol`、`description`、`createdOn`、`image`、`website`、`twitter`、`telegram`。图片和社交链接保存为字段字符串，不继续下载对应内容。

| 表 | 行数 | 一行表示什么 |
|---|---:|---|
| `launch_events.csv` | 4,668 | 一个纳入的创建事件 |
| `observation_plan.csv` | 18,672 | 一个事件在一个观察点的计划 |
| `request_attempts.csv` | 60,779 | 一次请求尝试或路线拒绝 |
| `response_snapshots.csv` | 16,744 | 一份响应的摘要、大小、时间与解析状态 |
| `field_observations.csv` | 133,888 | 一个成功解析响应上的一个登记字段 |
| `coverage_ledger.csv` | 18,672 | 一个事件在一个观察点的终态 |

事件、计划与账本通过 `event_key` 和 `checkpoint` 关联；请求、响应和字段通过 `request_id` 关联。请求表用 `attempt` 区分多次尝试。

`presence=present` 只表示 JSON 中存在该键，值可能是 `null`；`absent` 表示成功解析的 JSON 中没有该键。请求失败不等于字段不存在，不应将失败观察填为八个缺失字段。

## 5. 仍需处理的问题

### 5.1 完成状态与覆盖范围

现有队列全部观察已完成，但原始校验保留两条关于同一组 4 笔未取回交易的提示。这不是 8 笔交易，当前状态继续保留 `INCOMPLETE`。

4 笔是已知未解决的交易，不构成所有可能遗漏的上限。要主张完整覆盖，需要独立枚举窗口内的创建指令，与发布事件键比较并记录差集。

### 5.2 响应快照对账

16,748 条传输成功记录对应 16,744 条快照，其中 16,736 条为 `json_ok`，8 条为 `parse_error`。另有 4 个 `request_state=success` 的账本检查点没有对应快照，也被记为 `parse_failed`。

因此，12 次解析失败不能全部写成“返回正文不是合法 JSON”。应结合集群原始响应和日志核对这 4 个缺少快照的检查点。本次整理保留实采表和原有校验状态，不补造记录。

### 5.3 发布与复现边界

精简包不含第三方原始响应正文，也省略了与 CSV 重复的 `request_attempts.jsonl`。原始 manifest 仍列出该 JSONL，清单保留原样。现存六张 CSV 和校验文件均可与 manifest 核对。

没有正文，不能仅靠此包重新解析历史 JSON 或重算正文哈希。离线 fixture 验证流程；网络再次请求是新的观察，不能保证返回历史字节。

下一步应处理未解决交易、独立覆盖比较、响应快照对账和实际请求延迟，再依据本轮数据完成论文的 Technical Validation、Usage Notes、正式存储与 DOI 信息。
